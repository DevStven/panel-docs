# Интеграции и API

Этот документ описывает внешние интерфейсы панели: API, подписки, webhooks и MCP.

Для общей карты документации см. [panel-overview.ru.md](./panel-overview.ru.md).

## Какие внешние интерфейсы есть у панели

CELERITY-panel поддерживает несколько независимых способов внешнего доступа:

- REST API для автоматизации и внешних сервисов;
- subscription endpoints для клиентских приложений;
- webhooks для событийной интеграции;
- MCP для AI-ассистентов;
- служебные auth и agent-интерфейсы для узлов и backend-компонентов.

Важно разделять админский UI-доступ и интеграционный доступ. Они решают разные задачи и требуют разных моделей безопасности.

## REST API

REST API подходит для системной автоматизации.

Типовые сценарии:

- создание, изменение и отключение пользователей;
- управление узлами;
- работа с cascade links;
- чтение статистики и служебных статусов;
- запуск некоторых операций синхронизации и сопровождения.

### Практика безопасного доступа

- используйте отдельный API key на каждую интеграцию;
- ограничивайте scopes до минимально необходимых;
- по возможности ограничивайте доступ по IP;
- не используйте универсальный ключ для нескольких независимых систем.

### Что обычно автоматизируют через API

- биллинг или CRM;
- provisioning пользователей;
- служебные панели мониторинга;
- внутренние админские скрипты;
- поддерживающие процессы вокруг узлов и групп.

### Основные поверхности REST API

Ниже приведены основные интеграционные зоны API панели:

| Поверхность | Назначение |
|-------------|------------|
| `/api/users` | CRUD пользователей, статусы, лимиты, устройства и связанные операции |
| `/api/nodes` | CRUD узлов, sync, setup, config и служебные действия по инфраструктуре |
| `/api/cascade` | Cascade links, topology, deploy и reconnect-сценарии |
| `/api/files` и связанные subscription endpoints | Выдача клиентских подписок и форматов конфигурации |
| `/api/mcp` | MCP JSON-RPC endpoint для AI-клиентов |
| `/api/auth` | Служебный auth callback для узлов Hysteria |

Практически это означает, что REST API в панели делится на две категории:

- обычные интеграционные CRUD-вызовы для внешней автоматизации;
- служебные endpoints, которые являются частью внутренней архитектуры панели и не должны вызываться сторонними системами без необходимости.

## API keys и scopes

API keys - основной механизм внешней авторизации.

Они позволяют:

- разделять права между интеграциями;
- быстро отзывать доступ без смены пароля администратора;
- ограничивать срок жизни ключа;
- задавать scope-based доступ к возможностям панели.

Практический принцип: если интеграции нужно только читать пользователей, не выдавайте ей доступ к узлам, webhook-настройкам или операциям записи.

### Доступные scopes

Панель поддерживает следующие scopes API keys:

| Scope | Что разрешает | Типичный сценарий |
|-------|----------------|-------------------|
| `users:read` | Чтение пользователей и связанных выборок | CRM, биллинг, отчёты по пользователям |
| `users:write` | Создание, изменение, отключение, удаление пользователей и действия с устройствами | provisioning, lifecycle management |
| `nodes:read` | Чтение узлов, topology и части инфраструктурных данных | мониторинг, inventory, diagnostics |
| `nodes:write` | Изменение узлов, групп, cascade links, SSH-операции | инфраструктурная автоматизация, setup, deploy |
| `stats:read` | Статистика, группы, логи и агрегированные служебные данные | dashboards, отчёты, read-only audit |
| `sync:write` | Системные операции: sync all, clear cache, backup, kick user | ops automation, controlled maintenance |
| `mcp:enabled` | Доступ к MCP endpoint | Claude Desktop, Cursor, другие MCP-клиенты |

### Как scopes применяются на практике

Важно понимать несколько особенностей:

- `query` в MCP не имеет одного общего scope: требуемый доступ зависит от ресурса;
- чтение групп в MCP фактически привязано к `stats:read`;
- topology через MCP требует `nodes:read`;
- destructive или операционные действия должны отделяться в отдельные ключи от обычных read-only интеграций.

### Рекомендуемые наборы scopes

| Интеграция | Рекомендуемый минимум |
|------------|------------------------|
| Внешний CRM или биллинг | `users:read`, при необходимости `users:write` |
| Сервис мониторинга | `nodes:read`, `stats:read` |
| Ops automation | `nodes:write`, `sync:write` |
| MCP client | `mcp:enabled` и только те scopes, которые нужны конкретному AI workflow |

### Ограничения ключей помимо scopes

У API key есть не только scopes, но и дополнительные ограничения:

- `allowedIPs` - список разрешённых IP-адресов;
- `rateLimit` - лимит запросов на ключ;
- `expiresAt` - срок действия;
- `active` - быстрый soft revoke без удаления истории ключа.

Для production-интеграций имеет смысл использовать все четыре механизма одновременно, а не только scopes.

## Subscription endpoints

Subscription endpoints предназначены для конечных клиентов и их приложений.

Панель поддерживает выдачу подписок в нескольких форматах, включая сценарии с автоопределением формата по клиенту.

Это важно понимать так:

- подписка - отдельный интерфейс, не равный REST API;
- её потребители - клиентские приложения и сами пользователи;
- поведение подписки зависит не только от пользователя, но и от групп, настроек Subscription и конфигурации узлов.

### Что стоит документировать и проверять в интеграциях

- какой токен используется для выдачи подписки;
- как ротируется subscription token;
- какой формат ожидает клиентское приложение;
- как меняется поведение после изменения групп, routing и HAPP-настроек.

## Webhooks

Webhooks позволяют получать события панели во внешнюю систему.

Типовые категории событий:

- изменения пользователей;
- события, связанные с узлами;
- операции синхронизации и смежные служебные сигналы.

### Для чего это используют

- отправка уведомлений;
- аудит действий;
- обновление внешнего CRM или биллинга;
- реакция на проблемы узлов и синхронизации.

### Практические правила

- включайте только нужные события;
- защищайте обработчик через shared secret и проверку подписи;
- закладывайте обработку недоступности webhook endpoint;
- не отправляйте события напрямую в критичные бизнес-процессы без буфера и повторной валидации.

### Модель доставки

Webhook delivery в панели устроен так:

- доставка асинхронная и non-blocking;
- таймаут запроса - 5 секунд;
- ошибки доставки логируются, но не останавливают основную работу панели;
- retry-механизм на стороне панели не предусмотрен;
- фильтрация по событиям настраивается через Settings, пустой список означает доставку всех событий.

Из этого следует, что webhook consumer должен быть идемпотентным и готовым к единичным потерям доставки.

### Подпись и заголовки

Панель отправляет webhook с HMAC-SHA256 подписью и следующими заголовками:

| Заголовок | Значение |
|-----------|----------|
| `Content-Type` | `application/json` |
| `X-Webhook-Event` | имя события |
| `X-Webhook-Timestamp` | unix timestamp в секундах |
| `X-Webhook-Signature` | `sha256=<hmac>` |
| `User-Agent` | `C3-Celerity-Webhook/1.0` |

Формула подписи на принимающей стороне:

```text
expected = HMAC-SHA256(secret, timestamp + "." + rawBody)
```

Сравнивать нужно именно raw body, а не уже разобранный JSON.

### Формат payload

Webhook body отправляется как JSON следующего вида:

```json
{
	"event": "user.created",
	"timestamp": "2026-05-13T12:34:56.000Z",
	"data": {
		"userId": "demo"
	}
}
```

`data` зависит от конкретного события и должен трактоваться как event-specific payload.

### Поддерживаемые webhook events

| Event | Когда отправляется |
|-------|--------------------|
| `user.created` | Создан новый пользователь |
| `user.updated` | Изменены поля пользователя |
| `user.deleted` | Пользователь удалён |
| `user.enabled` | Пользователь включён |
| `user.disabled` | Пользователь отключён |
| `user.traffic_exceeded` | Пользователь превысил лимит трафика |
| `user.expired` | Пользователь истёк по сроку действия |
| `user.device_added` | Для пользователя впервые зарегистрировалось новое HWID-устройство |
| `user.device_limit_reached` | Достигнут лимит устройств по HWID |
| `node.online` | Узел перешёл в online |
| `node.offline` | Узел стал offline |
| `node.error` | Узел перешёл в error |
| `sync.completed` | Завершилась операция синхронизации |

### Особенность `user.device_limit_reached`

Это событие дедуплицируется в памяти процесса панели: пока процесс не перезапущен или флаг не очищен административным действием, повторные webhook для того же пользователя не отправляются. Для внешней системы это означает, что событие подходит для alerting, но не как счётчик всех повторных блокировок.

### Тестовая отправка

В панели есть отдельная test-доставка webhook. Она использует событие `test` и payload с диагностическим сообщением. Это служебный сценарий проверки канала, а не бизнес-событие панели.

## MCP

MCP делает панель доступной для AI-ассистентов и управляемых рабочих сценариев.

### Что MCP даёт

- чтение состояния панели;
- работу с users, nodes, groups и cascade;
- доступ к статистике и логам;
- запуск подготовленных prompts и административных сценариев;
- работу в совместимом AI-клиенте без прямого захода в UI.

### Когда MCP уместен

- для операторских задач с человеческим контролем;
- для аудита конфигурации;
- для быстрых выборок и диагностических запросов;
- для вспомогательных workflow в Claude Desktop, Cursor и похожих клиентах.

### Когда MCP не стоит считать заменой UI

- при первых production-изменениях;
- при сложных cascade-перестройках;
- при операциях restore и destructive maintenance;
- когда требуется визуальная проверка topology, stats и конфигураций.

### MCP transport и доступ

Панель реализует MCP по спецификации `2024-11-05` и поддерживает два транспорта:

| Transport | Endpoint | Когда использовать |
|-----------|----------|-------------------|
| Streamable HTTP | `POST /api/mcp` | основной режим для современных MCP-клиентов |
| Legacy SSE | `GET /api/mcp/sse` + `POST /api/mcp/messages` | fallback для старых клиентов |

Авторизация:

- `Bearer <api_key>` с scope `mcp:enabled`;
- либо активная админская session cookie из панели.

### MCP methods

Поддерживаются стандартные методы:

- `initialize`
- `ping`
- `tools/list`
- `tools/call`
- `prompts/list`
- `prompts/get`

Для streaming операций панель использует SSE events:

- `message` - JSON-RPC ответ;
- `progress` - промежуточный прогресс long-running операции;
- `log` - служебный вывод, например SSH или setup;

### MCP tools

Ниже перечислены фактические tools, доступные через MCP:

| Tool | Что делает | Базовый scope |
|------|------------|---------------|
| `query` | Универсальное чтение `users`, `nodes`, `groups`, `stats`, `logs` | зависит от ресурса |
| `manage_user` | Create, update, delete, enable, disable, reset traffic | `users:write` |
| `manage_hwid_devices` | List, unlink, unlink_all для HWID-устройств | `users:write` |
| `manage_node` | Create, update, delete, sync, setup, reset status, update config | `nodes:write` |
| `manage_group` | Create, update, delete групп | `nodes:write` |
| `manage_cascade` | Create, update, delete, deploy, undeploy, reconnect для cascade links | `nodes:write` |
| `execute_ssh` | Одноразовое выполнение shell-команды по SSH | `nodes:write` |
| `ssh_session` | Интерактивная SSH session | `nodes:write` |
| `system_action` | `sync_all`, `clear_cache`, `backup`, `kick_user` | `sync:write` |
| `get_topology` | Полная topology активных узлов и cascade links | `nodes:read` |
| `health_check` | Uptime, sync status, cache stats, memory usage | без отдельного scope |

### Как работает `query`

`query` - это не один источник данных, а роутер на несколько ресурсов. Требуемый scope зависит от `resource`:

| `query.resource` | Что возвращает | Нужный scope |
|------------------|----------------|--------------|
| `users` | Пользователи, фильтры, пагинация, отдельный user report | `users:read` |
| `nodes` | Узлы, статусы, groups, при необходимости users/config | `nodes:read` |
| `groups` | Группы и их агрегаты | `stats:read` |
| `stats` | Summary, traffic snapshots, nodes, online users | `stats:read` |
| `logs` | Последние логи панели | `stats:read` |

### MCP prompts

В панели есть встроенные prompt templates, которые MCP client может получить через `prompts/list` и `prompts/get`:

| Prompt | Назначение |
|--------|------------|
| `panel_overview` | Общий обзор панели: health, users, nodes, issues |
| `audit_nodes` | Аудит узлов с рекомендациями по проблемным состояниям |
| `user_report` | Детальный отчёт по конкретному пользователю |
| `setup_new_node` | Пошаговое добавление и настройка нового узла |
| `troubleshoot_node` | SSH-диагностика проблемного узла |
| `manage_expired_users` | Работа с истёкшими и скоро истекающими пользователями |

### Практические границы MCP

MCP особенно полезен для чтения состояния, guided operations и полуавтоматических админских сценариев. Но destructive и инфраструктурно чувствительные действия всё равно требуют человеческой проверки:

- `manage_cascade` и `manage_node` могут менять production-связность;
- `execute_ssh` и `ssh_session` фактически дают инфраструктурный shell-доступ;
- `system_action.backup` безопаснее, чем `clear_cache` или массовые sync-операции, но тоже относится к ops surface;
- доступ по `mcp:enabled` нельзя считать безопасным сам по себе без дополнительных scopes и IP-ограничений.

Подключение MCP подробно разобрано в [mcp-user-guide.ru.md](./mcp-user-guide.ru.md).

## Внутренние и служебные интерфейсы

Кроме пользовательских интеграций, панель использует специальные интерфейсы для своей работы.

Сюда относятся:

- auth callbacks от узлов;
- служебные запросы синхронизации;
- agent API для Xray-ориентированных сценариев;
- внутренние механизмы статистики и health-check логики.

Обычно эти интерфейсы не предназначены для сторонних систем напрямую. Их нужно учитывать как часть общей архитектуры и доверенной зоны.

## Как выбирать интеграционный интерфейс

Используйте простое правило:

- нужен машинный CRUD и автоматизация - берите REST API;
- нужно отдать конфигурацию клиенту - используйте subscription endpoint;
- нужна реакция на событие - используйте webhook;
- нужен AI-assisted доступ администратора - используйте MCP.

## Минимальные требования безопасности

1. Не передавайте административные секреты через небезопасные каналы.
2. Разделяйте ключи по интеграциям и срокам жизни.
3. Логируйте внешние операции в своей стороне.
4. Проверяйте, что scopes и IP restrictions соответствуют реальной задаче.
5. Не смешивайте клиентские subscription tokens с административными ключами доступа.
