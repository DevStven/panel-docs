# Продвинутые сетевые возможности

Этот документ описывает функции панели, которые требуют понимания сетевой схемы, ролей узлов и последствий для маршрутизации.

Для общей навигации используйте [panel-overview.ru.md](./panel-overview.ru.md).

## Когда нужен этот гайд

Переходите к этому документу, если вы:

- строите cascade topology;
- используете Network Map как рабочий инструмент диагностики;
- включаете ACL и routing rules;
- настраиваете load balancing;
- используете Xray-specific параметры, extra inbounds или REALITY;
- применяете custom config override;
- работаете с SNI scanner и нестандартными схемами доступа.

## Cascade topology

Cascade позволяет разделить точку входа и точку выхода трафика между разными узлами.

Типовые причины использования:

- клиент должен подключаться к узлу в определённой сети или юрисдикции;
- реальный выход трафика должен идти через другой узел;
- нужна многоузловая схема с relay или отдельной ролью ingress/egress.

### Базовые роли

- Portal - входная точка, куда приходит клиентский трафик.
- Bridge - выходная сторона, через которую трафик покидает цепочку.
- Relay - промежуточный узел в более сложной схеме.
- Standalone - обычный узел без cascade-роли.

### Что важно не перепутать

Ошибка в ролях portal и bridge обычно ломает всю схему. Документация и UI называют эти роли явно не случайно: они определяют направление соединений и порядок связи между узлами.

### Forward и Reverse

Панель поддерживает два принципиально разных режима:

- Reverse - bridge инициирует туннель к portal;
- Forward - portal строит цепочку через relay к bridge.

Эти режимы нельзя смешивать в одной цепочке как взаимозаменяемые.

### Практические правила

- перед deploy понимаете, где вход, где выход и кто кому доступен по сети;
- после deploy проверяйте фактический exit IP;
- не меняйте роли на production без проверки связности;
- используйте Network Map как обязательную визуальную проверку, а не как вторичный экран.

## Network Map

Network Map - это рабочая карта связей между узлами, а не просто визуальный режим списка.

Она помогает:

- видеть структуру цепочек и статусы связей;
- отслеживать проблемные переходы между узлами;
- контролировать health links после redeploy;
- быстро понимать, какой узел участвует в какой роли.

Map особенно полезна после массовых изменений узлов, после setup и после правок cascade links.

## Routing и ACL

Панель поддерживает правила маршрутизации и фильтрации трафика.

Через routing/ACL можно:

- блокировать нежелательные домены и сети;
- направлять трафик по специальным правилам;
- использовать geosite и geoip-подходы;
- управлять клиентским поведением на уровне выдаваемой конфигурации.

### Когда применять

- для рекламы и базовой фильтрации;
- для региональных ограничений;
- для особых сценариев direct/block;
- для отделения внутреннего и внешнего трафика.

### Риски

- ошибка в правилах ломает доступ сразу у многих пользователей;
- неверные DNS-параметры и слишком агрессивные блокировки сложно отлаживать по жалобам клиентов;
- после изменения routing правил нужно проверять реальные подписки, а не только форму в Settings.

## Load balancing

Load balancing распределяет пользователей и трафик между узлами с учётом нагрузки.

Практически это помогает:

- уменьшать перегрузку одного узла;
- скрывать overloaded nodes из обычного потока выдачи;
- использовать ranking и приоритеты как управляемый механизм, а не ручной список.

### Что учитывать

- балансировка работает лучше, когда статусы узлов актуальны;
- неправильные rankingCoefficient или скрытие overloaded nodes могут неожиданно уменьшить доступный пул для пользователей;
- после включения балансировки стоит проверить выдачу подписки для разных групп.

## Xray-specific возможности

Для Xray узлов панель покрывает больше сложных сценариев, чем базовый VLESS endpoint.

### Что относится к расширенным функциям

- REALITY;
- extra inbounds;
- transport и security options;
- outbounds и chained routing;
- agent status и служебная диагностика.

### Когда быть особенно осторожным

- при автоматической генерации и смене REALITY-параметров;
- при добавлении extra inbounds на production-узел;
- при каскадных схемах, где Xray участвует как tunnel layer;
- при редактировании custom JSON без промежуточной проверки config preview.

## Hysteria-specific возможности

Для Hysteria узлов панель также поддерживает расширенную конфигурацию.

Сюда относятся:

- параметры ACME и challenge modes;
- masquerade-поведение;
- resolver и speed test options;
- sniffing и QUIC tuning;
- ограничения, влияющие на auth и online accounting.

Не каждая установка требует ручной тюнинг этих опций. Если базовый сценарий уже работает стабильно, advanced-параметры стоит менять только под конкретную задачу.

## SNI scanner

SNI scanner помогает подобрать или проверить SNI-цели в сценариях, где это влияет на доступность или маскировку соединения.

Используйте его:

- при первичной подготовке нестандартной Xray-конфигурации;
- при отладке проблем с конкретными сетями;
- при подборе более устойчивого внешнего профиля соединения.

SNI scanner - диагностический инструмент. Он не заменяет проверку работы клиента после деплоя.

## Custom config override

Custom config override даёт максимум свободы, но почти полностью переносит ответственность на администратора.

### Что это означает на практике

- UI перестаёт быть главным источником валидации;
- можно задать схему, которую панель обычно не даёт собрать формами;
- вместе с гибкостью растёт риск скрытой ошибки.

### Когда использовать

- когда стандартный UI реально не покрывает нужный сценарий;
- когда у вас уже есть проверенный конфиг;
- когда вы готовы сопровождать такую конфигурацию вручную.

### Когда не использовать

- для первого знакомства с панелью;
- для массовых production-изменений без тестового узла;
- когда ту же цель можно собрать штатными настройками и config preview.

## Минимальный безопасный порядок для advanced-изменений

1. Проверить текущую топологию и состояние узлов.
2. Подготовить rollback-сценарий.
3. Менять одну сложную переменную за раз.
4. Сразу смотреть config preview и фактический deploy результат.
5. Проверять exit path, логические связи и пользовательские подписки.
