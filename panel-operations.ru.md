# Эксплуатация и обслуживание

Этот документ описывает операционные процедуры вокруг панели: backup, restore, обновления, безопасные изменения и послепроверки.

Для общей карты документации см. [panel-overview.ru.md](./panel-overview.ru.md).

## Основной принцип

Панель объединяет UI, инфраструктурное управление, подписки и интеграции. Поэтому даже небольшое изменение в production может затронуть пользователей, узлы, внешние webhook-процессы и клиентские приложения.

Практический вывод: любое административное действие лучше оценивать как изменение рабочей системы, а не как локальную настройку формы.

## Backup

Backup - обязательная операция перед любыми изменениями повышенного риска.

### Когда backup обязателен

- перед restore;
- перед maintenance reset;
- перед массовыми правками routing или cascade;
- перед обновлением production;
- перед крупным переносом пользователей, групп или узлов.

### Что стоит проверять

- backup действительно создан и доступен;
- размер backup выглядит правдоподобно;
- при использовании S3 копия действительно ушла во внешнее хранилище;
- есть понятный способ быстро найти нужную копию позже.

## Restore

Restore - одна из самых опасных операций в панели.

Что нужно понимать заранее:

- текущая база заменяется содержимым backup;
- это может отменить свежие изменения пользователей, узлов, групп и настроек;
- внешние интеграции после restore могут увидеть устаревшее состояние;
- rollback после неудачного restore возможен только если у вас есть backup текущего состояния.

### Безопасный порядок

1. Создайте backup текущего состояния перед восстановлением.
2. Сообщите команде о коротком окне обслуживания.
3. Зафиксируйте, из какой именно копии восстанавливаетесь.
4. После restore проверьте login, users, nodes, subscriptions и integrations.

## Обновления

Для обновления production используйте отдельный пошаговый гайд: [safe-update.ru.md](./safe-update.ru.md).

Здесь важно зафиксировать операционный смысл:

- обновление панели не ограничивается стартом контейнера;
- после обновления нужно проверить не только UI, но и auth, nodes, subscriptions, API и webhooks;
- если используется cascade или Xray agent-сценарий, проверка должна быть шире, чем просто доступность страницы логина.

## Обслуживающие операции

К обслуживающим операциям относятся:

- очистка кэша;
- сброс накопленного трафика;
- очистка статистики;
- сервисные действия, меняющие состояние панели целиком.

### Когда их делать

- когда вы точно понимаете цель операции;
- когда есть backup;
- когда влияние на пользователей и отчёты допустимо;
- когда есть время на послепроверку.

### Когда их не делать

- в середине инцидента без понимания причины;
- сразу после большого релиза, если ещё нет baseline-проверок;
- без фиксации того, какие данные должны сохраниться, а какие допустимо потерять.

## Работа с узлами в эксплуатации

Операционная работа с узлами включает:

- health checks;
- ручную диагностику через terminal;
- массовые команды через broadcast terminal;
- setup и redeploy узлов;
- проверку cascade links и сетевой связности.

### Практические рекомендации

- сначала проверяйте один узел, потом запускайте массовые действия;
- используйте broadcast terminal только для повторяемых безопасных команд;
- после setup или redeploy проверяйте не только статус узла, но и реальную пользовательскую доступность.

## После любого заметного изменения

Минимальная послепроверка должна включать:

1. Вход администратора в панель.
2. Статусы узлов в Nodes.
3. Выдачу подписки хотя бы для одного тестового пользователя.
4. Базовую работу API или webhook, если они используются.
5. Dashboard, Stats и System на предмет новых ошибок.

## Частые операционные риски

- считать, что backup есть, не проверив его наличие и читаемость;
- запускать restore как способ посмотреть старое состояние;
- выполнять maintenance reset без понимания влияния на отчёты и лимиты;
- менять cascade и одновременно обновлять узлы, теряя возможность локализовать проблему;
- использовать terminal как замену управляемому rollout-процессу.

## Чек-лист перед опасным действием

- есть свежий backup;
- понятен ожидаемый результат;
- понятен способ отката;
- выбран низконагруженный момент;
- определён минимальный набор послепроверок.
